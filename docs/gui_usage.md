# 可视化仿真实验界面操作说明

本文档说明 `python main.py` 启动后的可视化界面如何使用，包括实验场景、求解方式、参数范围输入格式，以及推荐的实验操作流程。

## 1. 启动方式

请先进入项目目录，并确认当前 Python 环境为 `pavane`：

```bash
conda activate pavane
python main.py
```

程序会打开“城际配送系统仿真实验平台”窗口。窗口左侧用于选择实验场景、求解方式和参数范围，右侧用于预览实验计划和查看运行日志。

如果不希望打开图形界面，也可以使用命令行模式：

```bash
python main.py --cli --scenario baseline --solver exact_mip --seeds 3
```

## 2. 界面区域说明

### 2.1 实验场景

实验场景决定系统自动生成哪些算例。可以同时勾选多个场景。

| 场景 | 含义 | 典型用途 |
|---|---|---|
| 快速测试 `quick` | 生成一个小规模算例 | 检查模型、Gurobi、结果输出是否正常 |
| 小规模基准 `baseline` | 按多个小规模订单数生成算例 | 用精确 MIP 得到基准结果，为后续算法对比提供参照 |
| 规模扩展 `scale` | 按较大订单规模生成算例 | 测试模型或算法在大规模订单下的求解能力 |
| 灵敏度分析 `sensitivity` | 逐一改变关键参数生成算例 | 分析自动车数量、成本、人工车数量、时间窗、需求结构对结果的影响 |

界面右侧“实验计划预览”会显示当前选择会生成多少个算例，以及前 30 个算例的主要参数。

### 2.2 求解方式

求解方式决定每个算例使用哪种算法求解。可以同时勾选多个求解器。

| 求解方式 | 当前状态 | 说明 |
|---|---|---|
| 精确 MIP `exact_mip` | 已实现 | 调用 `optimizer.py` 中的 Gurobi MIP 模型求解 |
| Rolling Horizon `rolling_horizon` | 预留接口 | 当前尚未实现正式算法，只用于后续算法扩展占位 |

为了保证算法比较公平，程序会对每个算例只生成一次订单数据，然后把同一份订单数据传给所有勾选的求解器。因此，如果同时勾选 `exact_mip` 和未来实现的 `rolling_horizon`，两者使用的是同一输入数据。

## 3. 参数范围输入说明

左侧“参数范围”区域的输入框支持两类格式：

| 类型 | 输入示例 | 说明 |
|---|---|---|
| 单个整数或小数 | `500`、`100`、`15.0` | 用于时间限制、单个车辆数等 |
| 逗号分隔列表 | `20, 50, 100` | 用于多个订单规模、多个成本水平等 |
| 时间窗区间列表 | `0-1, 0-3, 0-5` | 每一项表示一个随机缓冲区间 |

输入逗号分隔列表时，可以有空格，也可以没有空格。例如 `20,50` 和 `20, 50` 都可以。

### 3.1 每个水平随机种子数

字段名：`每个水平随机种子数`

含义：每个参数水平重复生成多少个随机算例。

示例：

```text
3
```

如果 `baseline 订单规模 = 20, 50`，随机种子数为 `3`，则 baseline 会生成：

```text
2 个订单规模 × 3 个随机种子 = 6 个算例
```

建议：

| 目的 | 推荐值 |
|---|---:|
| 快速调试 | 1 |
| 论文初步实验 | 3 |
| 稳健性更强的正式实验 | 5-10 |

### 3.2 单算例时间限制（秒）

字段名：`单算例时间限制(秒)`

含义：每个 Gurobi 算例最多求解多少秒。

示例：

```text
500
```

建议：

| 场景 | 推荐时间 |
|---|---:|
| quick | 60-300 秒 |
| baseline | 300-600 秒 |
| scale | 500-1800 秒 |
| sensitivity | 300-1000 秒 |

如果达到时间限制但已有可行解，结果表中通常会出现 `MIP_Gap > 0`。

### 3.3 quick 订单数

字段名：`quick 订单数`

含义：快速测试场景生成的订单数量。

示例：

```text
20
```

建议保留较小值，例如 `10`、`20`、`30`，用于检查程序是否能完整运行。

### 3.4 baseline 订单规模

字段名：`baseline 订单规模`

含义：小规模基准实验使用的订单数量列表。

示例：

```text
20, 50
```

用途：这些算例一般用于与精确 MIP 的最优解对比。后续实现 rolling horizon 等算法后，可以使用同一批 baseline 算例计算算法 Gap。

### 3.5 scale 订单规模

字段名：`scale 订单规模`

含义：规模扩展实验使用的订单数量列表。

示例：

```text
100, 200, 500, 1000
```

用途：观察订单数量增加后，求解时间、MIP Gap、服务率、车辆使用量如何变化。

### 3.6 scale 自动车数/城市

字段名：`scale 自动车数/城市`

含义：规模扩展实验中，每个城市初始可用的自动驾驶车辆数量。

示例：

```text
50
```

该值会设置为：

```python
N_auto = {1: 50, 2: 50}
```

### 3.7 scale 人工车数/城市

字段名：`scale 人工车数/城市`

含义：规模扩展实验中，每个城市可用的人工驾驶车辆数量。

示例：

```text
100
```

该值会设置为：

```python
N_manual = {1: 100, 2: 100}
```

### 3.8 灵敏度订单数

字段名：`灵敏度订单数`

含义：所有灵敏度分析算例使用的订单数量。

示例：

```text
100
```

建议先使用 `50` 或 `100` 做初步测试，再根据求解速度提高规模。

### 3.9 灵敏度基准自动车

字段名：`灵敏度基准自动车`

含义：灵敏度分析中，除“自动车数量水平”这一组外，其余灵敏度实验默认使用的每城市自动车数量。

示例：

```text
30
```

### 3.10 灵敏度基准人工车

字段名：`灵敏度基准人工车`

含义：灵敏度分析中，除“人工车数量水平”这一组外，其余灵敏度实验默认使用的每城市人工车数量。

示例：

```text
60
```

### 3.11 自动车数量水平

字段名：`自动车数量水平`

含义：灵敏度分析中用于测试自动驾驶车辆规模影响的取值列表。

示例：

```text
0, 5, 10, 20, 30, 50
```

程序会分别构建：

```python
N_auto = {1: 0, 2: 0}
N_auto = {1: 5, 2: 5}
...
```

用途：分析自动车数量增加是否降低成本、提高服务率，以及是否存在边际收益递减。

### 3.12 自动车成本水平

字段名：`自动车成本水平`

含义：灵敏度分析中用于测试自动驾驶车辆单位成本影响的取值列表。

示例：

```text
5, 10, 15, 20, 25
```

用途：分析自动驾驶技术成本下降后，系统是否更倾向于使用自动车。

### 3.13 人工车数量水平

字段名：`人工车数量水平`

含义：灵敏度分析中用于测试城市内人工配送运力影响的取值列表。

示例：

```text
10, 20, 30, 50, 80
```

用途：判断系统瓶颈是否在城市内集散环节。

### 3.14 时间窗缓冲水平

字段名：`时间窗缓冲水平`

含义：控制订单时间窗松紧程度。每一项形如 `a-b`，表示随机缓冲时间从 `a` 到 `b` 个离散时间段中抽取。

示例：

```text
0-1, 0-3, 0-5, 0-8
```

解释：

| 输入 | 含义 |
|---|---|
| `0-1` | 时间窗很紧 |
| `0-3` | 时间窗较紧 |
| `0-5` | 默认水平 |
| `0-8` | 时间窗较宽松 |

用途：分析时间窗越紧时，未服务率和成本是否上升。

### 3.15 大订单比例水平

字段名：`大订单比例水平`

含义：生成随机订单时，大宗货物订单出现的概率。

示例：

```text
0.1, 0.3, 0.5, 0.7
```

当前订单生成逻辑中：

| 订单类型 | 数量范围 |
|---|---|
| 小订单 | 10-50 |
| 大订单 | 100-300 |

用途：分析需求结构变重后，车辆容量和转运约束是否成为主要瓶颈。

## 4. 推荐操作流程

### 4.1 快速检查模型

1. 只勾选 `quick`。
2. 只勾选 `精确 MIP (Gurobi)`。
3. 保持 `quick 订单数 = 20`。
4. 点击“刷新预览”。
5. 点击“批量运行”。

如果运行成功，说明环境、Gurobi、数据生成和结果保存流程基本正常。

### 4.2 跑小规模基准实验

1. 勾选 `小规模基准 baseline`。
2. 取消 `quick`。
3. 设置 `baseline 订单规模 = 20, 50`。
4. 设置 `每个水平随机种子数 = 3` 或 `5`。
5. 点击“批量运行”。

这类结果适合作为论文中“精确 MIP 基准结果”。

### 4.3 跑规模扩展实验

1. 勾选 `规模扩展 scale`。
2. 设置 `scale 订单规模 = 100, 200, 500, 1000`。
3. 根据机器性能设置时间限制，例如 `500` 或 `1000`。
4. 点击“批量运行”。

如果大规模算例经常达到时间限制，应重点观察 `MIP_Gap` 和 `Solve_Time_Sec`。

### 4.4 跑灵敏度分析

1. 勾选 `灵敏度分析 sensitivity`。
2. 设置一个适中的 `灵敏度订单数`，例如 `100`。
3. 根据研究重点调整各个水平列表。
4. 点击“刷新预览”确认算例数量。
5. 点击“批量运行”。

灵敏度分析算例数量通常较多，建议先用 `每个水平随机种子数 = 1` 试跑，再增加到 `3` 或 `5`。

## 5. 常见问题

### 5.1 为什么预览中“预计结果行数”大于“场景数量”？

因为每个算例会被每个选中的求解器运行一次：

```text
预计结果行数 = 算例数量 × 求解器数量
```

例如 6 个 baseline 算例，同时勾选 2 个求解器，则结果表会有 12 行。

### 5.2 Rolling Horizon 为什么没有结果？

目前 `rolling_horizon` 只是预留接口，尚未实现正式算法。它存在的目的是提前搭好可比较的实验框架。后续实现算法后，只需要在 `solvers.py` 中补全对应求解器。

### 5.3 为什么有些结果全部未服务？

这通常说明当前参数下“放弃服务的惩罚成本”低于派车运输成本。可以考虑提高 `config.py` 中的 `penalty_lost`，或降低车辆单位成本后重新测试。

### 5.4 界面卡住怎么办？

求解过程在后台线程运行，界面通常仍可滚动查看日志。但如果 Gurobi 正在处理大规模算例，系统响应可能变慢。建议先用较小订单规模和较短时间限制试跑。

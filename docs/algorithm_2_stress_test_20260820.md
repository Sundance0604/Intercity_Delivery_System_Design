# Algorithm 2 配对压力测试报告（2026-08-20）

## 1. 比较对象

本报告中的两种流程定义为：

- A1+MIP：Algorithm 1 候选网络剪枝 + reduced MIP；
- A1+A2+MIP：Algorithm 1 候选网络剪枝 + Algorithm 2 经济型部分暖启动 + 同一个 reduced MIP。

Algorithm 2 不单独运行。两组使用相同订单、相同随机种子、相同模型参数和相同总时间预算。

## 2. 压力测试设置

- 城市对：Los Angeles–San Francisco；
- 订单规模：200、500、1000；
- 随机种子：6201、6202、6203；
- 每个流程总时间限制：30 秒；
- 预测窗口 H=8，滚动步长=2，扩展窗口 L=12，城际时间 tau=9；
- 丢失需求单位罚金=1；
- 求解环境：conda pavane，Gurobi 10.0.3。

完整结果位于 simulation/runs/R2S3。修复前的递增试验位于 simulation/runs/R2SP，1000单同实例修复复验位于 simulation/runs/R2SP2。

## 3. 压力测试暴露的问题及修复

最初的1000单试验中，A1+A2+MIP 在 t=4 触发 Algorithm 2 后，启发式构造耗时约38.47秒，MIP只剩约0.03秒，因此状态9时没有获得可行解。这不是 MIP Start 导致模型不可行，而是 Algorithm 2 没有硬时间上限。

已实施以下修复：

- Algorithm 2 单次构造预算默认不超过 heuristic_trigger_time_sec（当前为1秒）；
- 枚举候选选项和动态排序循环都检查硬截止时间；
- 至少为后续 MIP 保留0.5秒；
- 超时的部分构造仍作为非零部分 MIP Start 注入；
- 新增 heuristic_budget_sec、heuristic_time_limit_reached、ranked_orders_before_limit 和 heuristic_elapsed_sec 诊断。

修复后同一个1000单实例的两组都在30秒内获得可行 incumbent。Algorithm 2 两次触发的实际构造时间约为1.06秒和1.09秒，不再耗尽MIP预算。

## 5. 共同不可行实例的诊断与修复

500单、种子6202最初在两种流程的 t=4 窗口均返回Gurobi状态3，且Algorithm 2没有触发。IIS将冲突定位到历史人工弧 (3,4) 的容量约束：历史车辆数为0，但145个历史货流变量累计保留了 4.31e-6 的数值残差。

仅删除小变量后，失败推迟到 t=8。最小可行性松弛仍只有 4.29e-6，说明真实货量在取货、干线和配送阶段之间保留了微小浮点尾差。独立按阈值删除会破坏原本的阶段不等式。

最终修复采用按需数值重试：

- 车辆变量在提交时规范到整数，并清除不超过1e-6的纯数值货流；
- 正常窗口继续精确固定全部历史决策，保持Gurobi预处理效率；
- 仅当首次求解返回状态3且没有可行解时，对已提交连续货流开放正负1e-5的固定带并重求解一次；
- 未提交的历史变量仍精确固定为0，车辆变量始终精确固定；
- 曾尝试默认量化或默认固定带，但前者破坏聚合流量关系，后者显著削弱1000单模型的预处理，均未保留。

最终代码下，500单三个种子的两种流程均完成12个窗口。原失败种子6202仅从t=8开始触发数值重试，两组成本均为2293.3109，时间分别为9.82秒和10.34秒。500单可行率由2/3恢复为3/3，三种子平均成本均为2852.1036。

## 6. 当前结论

硬预算修复解决了Algorithm 2在大规模实例上反而耗尽求解时间的严重问题。200和500单的容易窗口会自动跳过Algorithm 2，因此不会重复此前的无效构造开销。1000单开始触发Algorithm 2，其平均MIP Gap有所下降，但最终成本没有稳定改善。

因此当前最稳妥的论文结论仍是：Algorithm 2是只在经验困难窗口中启用的自适应部分暖启动机制，而不是保证加速或降低成本的算法。下一阶段应增加1000单种子数并进行固定预算 incumbent 轨迹分析。
